# ADR · 驳回后禁止重报

> 状态：已裁决（2026-09-21）
> 分支：refactor/architecture-cleanup（v2.0 唯一主线）
> 关联：docs/prompt-v1退役与新框架迁移-20260921.md Phase 2

---

## 1. 背景 · 两个方向相反的提交

「被驳回（未录取，status=4）后能否重新报名」在两版代码中给出相反答案：

| 提交 | 分支 | 日期 | 行为 |
|------|------|------|------|
| `bda3348` | release/v1 | 8/6 | 未录取后**允许**重新报名（去掉第 4 步和查重接口的 STATUS_REJECTED 拦截） |
| `dc9c0b7` | refactor/architecture-cleanup | 8/23 | 被驳回后同一身份证/手机号/同班**禁止**重报（三层防重全部加上 STATUS_REJECTED） |

v1 已于 2026-09-21 退役，不再作为参考基准；新框架为唯一主线，需要明确裁决。

## 2. 裁决结果

**以「禁止重报」为准，但严格限定语义边界：**

| 场景 | 裁决 |
|------|------|
| 被驳回后重报**同一个班** | ❌ **禁止**（点击提示"未录取无法再次报名"） |
| 被驳回后报**其他班** | ✅ **允许** |

> ⚠️ 语义边界是本次裁决的核心：禁的是「同班重报」，不是「一票否决」。把"报其他班"也禁掉属于扩大化禁止，那是改需求不是修 bug（v1 代码注释明确"被驳回(4)后应能报其他班，所以这里不查 STATUS_REJECTED"）。

## 3. 理由

1. **单一主线**：v1 已退役，refactor 分支的新框架是唯一准绳，冲突以新框架为准。
2. **新框架规则更严格且与产品意图一致**：线下报名场景中，"未录取"意味着该生在该班本轮未被选中，放任同班重报会造成名额反复占放、审核记录错乱（如 ***REMOVED*** 案例——低代码平台按审核意见分组批量同步被"已处理过"记录连累）。
3. **与防重三层设计一致**：防重三层（身份证全局 / 手机号全局 / 同班）中，前两层管"一个学生一个班"的全局约束，第三层管"同一班不重复占位"。被驳回只清退"同班"占用，不动全局资格——所以 STATUS_REJECTED 只应出现在第三层。
4. **已撤回(status=2)仍可重报**：撤回是学生主动行为，不产生审核结论，不在此规则内（新旧两版一致）。

## 4. 代码落点（已按此修改）

| 位置 | 修改 |
|------|------|
| `ApplicationService.submit()` | 身份证/手机号全局唯一 → 只查 `STATUS_APPLIED, STATUS_ENROLLED`；同班防重 → 查 `+ STATUS_REJECTED`，并被驳回时提示"未录取无法再次报名" |
| `ApplicationService.checkDuplicate()` | 同上（查重接口与提交口径一致） |
| `ApplicationService.syncFromLowCode()` | 新增防重只拦"有效报名(1/3)"；status=4 的新增记录放行（可报其他班） |
| 测试 | `ApplicationServiceTest` 覆盖"同班驳回拒绝"与"状态4可新增"两条路径 |
