## 一、系统总体架构

特色班报名系统为**双库双端 + 定时/手动同步**架构，服务「新生特色班报名」全流程。

### 1.1 双端 / 双库一览

| 角色 | 载体 | 用户 | 数据库 | 职责 |
| --- | --- | --- | --- | --- |
| **学生端** | 外网 H5/Web（`enroll-web`）+ 后端 `enroll-server` | 学生本人 | 外网库 `enroll_db` | 报名、撤回/修改、查「我的报名」、看须知/公告、查年份 |
| **管理端** | 内网低代码平台（CodeWave，NASL） | 特色班管理员 / 教师 | 内网库 `smart_academic_affairs` | 报名须知、公告栏、班级+类别、学生录取、按年查报名、批量软删恢复、教师-班级映射 |
| **教务库**（只读引用） | 智慧教务平台的库 | — | `SmsStudent` 等 | 录取设置页做「学号/学院/专业」补全匹配 |

> ⚠️ **网络隔离**：外网库与内网库物理分开、网络隔离，**低代码平台不能直连外网库**，一切跨库数据同步都经由外网 `enroll-server` 提供的 HTTP API。

### 1.2 关键架构原则

1. **双库各自维护一套同名 `ssc_` 前缀表**，主键各自独立自增、值不对应；靠 `outer_id` 跨库映射（**两库 `outer_id` 语义方向相反**，详见第五节）。
2. **只允许 POST / GET**（动数据 = POST、查数据 = GET），禁止 PUT/DELETE/PATCH——这是为对接内网低代码平台（HTTP 客户端能力有限）的**硬约束**。
3. **数据可追踪**：`classes.source` / `applications.source` 标记数据来源（`student`=学生自报 / `admin`=管理员建 / `sync`=低代码同步）。
4. **管理端 UI 不在外网仓库**：`enroll-web` 只保留学生端 4 个页面；旧开发期 `AdminLogin/AdminDashboard` 已移除，管理员界面完全由低代码平台承担。
5. **低代码平台只服务管理员/教师**，**完全不涉及学生侧**。

### 1.3 整体数据流（一句话版）

```
学生(外网扫码/链接)
   │ 手机验证码登录 → 选班 → 报名
   ▼
外网 enroll-server ──写──▶ 外网库 enroll_db（权威：学生报名数据）
        ▲                                  │
        │ NASL 主动拉 applications/all      │ 存 6 张 ssc_ 表
        │ （低代码同步主链路）                ▼
内网低代码平台(NASL dataSynchronization) ── 内网库 smart_academic_affairs
        │ 班级/类别/报名须知 = 内网权威 → 全量覆盖推送外网
        │ 录取/未录取/软删   = 内网权威 → 分批回推外网
        ▼
教务库(只读)：录取设置页按 姓名+身份证 匹配 学号/学院/专业
```

## 三、运行依赖、认证与启动

### 3.1 运行依赖

| 依赖 | 用途 | 说明 |
| --- | --- | --- |
| MySQL | enroll-server 数据存储 | 外网 `enroll_db`（本地开发 `localhost:3306`，用户 `enroll` / 密码见部署配置） |
| **Redis** | 学生短信验证码缓存 | key 形如 `sms:login:{phone}`（TTL 5min）、`sms:gap:`(60s)、`sms:ip:`、`sms:err:`；后端用 `StringRedisTemplate`，**需可连 Redis** |
| 短信平台 | 发验证码短信 | 大汉三通 `http://***REMOVED***:8061`（账号在 `application*.yml` 的 `sms.*`，生产由堡垒机环境变量注入） |
| JWT | 登录态 | 管理员/学生各签发 token，均 24h 过期 |
| Maven / Node | 构建 | enroll-server 用 `mvnw.cmd`；enroll-web 用 npm |

> 🔧 **本地联调免短信/免 Redis**：把 `sms.test-mode` 配为 `true`，则任意手机号 + 验证码 `666666` 即可直接登录（不连 Redis、不发短信）。仅限本地测试，生产必须为 `false`。

### 3.2 认证体系（重要，前端与后端存在演进差异）

**管理员登录** `POST /api/auth/login`：
- Body `{username, password}`。默认开发期临时账号 `***REMOVED***` / `***REMOVED***`（可被环境变量 `AUTH_ADMIN_USER` / `AUTH_ADMIN_PASSWORD` 覆盖）。
- 登录成功：签发 `role=admin` 的 JWT（24h），**同时下发 httpOnly Cookie `admin_token`**（path=/api, secure, SameSite=Strict）+ 返回体带 `token`。
- ⚠️ 生产环境管理员应走智慧教务账号体系，`admin_token` 主要用于低代码平台同步时获取 API 凭证（NASL 第一步 `login()` 即取返回体的 `token` 拼 `Bearer`）。

**学生验证码登录** `POST /api/auth/login/sms`：
- 先 `POST /api/auth/send-code` 发码 → 校验码登录。
- 签发 `role=student` 的 JWT（sub=手机号），**同时设 httpOnly Cookie `student_token`**；返回含 `hasRegistration / status / classId / applyTime`。

> ⚠️ **两套并存的坑（接手必读）**：后端 S8 版本同时下发 httpOnly Cookie，但**当前外网前端实际仍用 `localStorage['student_token']` + `Authorization: Bearer` 请求头**（api.js / views 现状），并未走 `credentials:include` 依赖 Cookie。改安全策略/跨域时务必注意：**前后端在 Cookie 化上尚未完全对齐，两套机制并存**，不要假设只存在其中一种。

**JWT 拦截范围**：
- 后端拦截器**只拦 `/api/admin/**`**。
- 学生端 `my`/`me` 的 JWT 校验是 controller 内**手写解析请求头**（`role=student`）完成，不走全局拦截器。
- ⚠️ **安全边界提醒**：学生端 `submit` / `withdraw` / `update` 写接口后端**未强制 JWT**（历史遗留）。若需收紧需改造，交接时注意此点。

**验证码与限流（AuthService 源码级）**：
- 验证码存 Redis：`sms:login:{phone}`（5 分钟有效）、发送间隔 `sms:gap:`（60s）、IP 限流 `sms:ip:`（每分钟 10 次）、错误次数 `sms:err:`（5 次错误作废需重发）。
- IP 取值优先 `X-Forwarded-For`。
- `sms.test-mode=true` 时任意手机 + `666666` 直接登录。

> ℹ️ **无「改密码」接口**：系统不提供修改密码的能力。管理员密码 = 环境变量 `AUTH_ADMIN_USER` / `AUTH_ADMIN_PASSWORD`（默认 ***REMOVED*** / ***REMOVED***），想改只能改环境变量并重启；学生走短信验证码、本身无密码体系。接手时不要在 API 里找改密码端点——没有。

### 3.3 端口与代理

| 项 | 值 |
| --- | --- |

### 4.1 页面清单

| 页面（逻辑名） | 功能 | 数据同步按钮 |

### 4.3 录取设置选项卡的数据源（直连教务库，模板化 SQL）

录取配置页加载可录取学生名单时，从**内网库 JOIN 教务库**补全学号/学院/专业。核心 SQL（节选逻辑，含低代码平台变量）：

```sql
SELECT a.id, a.name AS studentName, a.idCard, a.gender, a.phone,
       a.hasPhysics, a.hasEnglish,
       IF(a.appliedCategory IS NULL OR a.appliedCategory='','未设置',a.appliedCategory) AS appliedCategory,
       a.status, a.auditComment, a.applyTime, a.round, a.enrollmentYear,
       c.name AS className,
       IFNULL(s.studentId,'暂无数据') AS studentId,
       IFNULL(deptCollege.departmentName,'暂无数据') AS affiliatedCollegeName,
       IFNULL(deptDepart.departmentName,'暂无数据') AS departName,
       IFNULL(prof.professionalName,'暂无数据') AS professionalName
FROM SscApplications a
INNER JOIN SscClasses c ON a.classId = c.id
LEFT JOIN SmsStudent s
       ON a.name = s.studentName COLLATE utf8mb4_unicode_ci
      AND a.idCard = s.identityCard COLLATE utf8mb4_unicode_ci
LEFT JOIN SysDepartmentInformation deptCollege ON s.affiliatedCollege = deptCollege.departmentId
LEFT JOIN SysDepartmentInformation deptDepart  ON s.depart           = deptDepart.departmentId
LEFT JOIN SysProfessionalCode prof ON s.professionalCode = prof.id
WHERE a.isDeleted = 0
  AND c.id IN ${visibleClassIdList}          -- 可见班级（教师映射过滤）
  AND a.status != 0 AND a.status != 2        -- 去掉 未报名 / 已撤回
  -- 其余为低代码平台动态注入的筛选：# if filter.xxx != '' → a.xxx like ${filter.xxx} ...
```

- 表归属：`SscApplications / SscClasses` = 低代码平台对内网库 `ssc_` 表的实体命名；`SmsStudent / SysDepartmentInformation / SysProfessionalCode` = **教务库**表（只读）。
- `${visibleClassIdList}` 与 `${filter.*}` 是低代码平台**页面级注入变量**；`# if / # end` 是 NASL 模板语法。这些属低代码平台内部机制，本高代码端不感知。

## 五、数据库双库设计与状态机

### 5.1 双库 6 表清单

两库各自维护一套同名表（前缀 `ssc_`）：`ssc_applications`、`ssc_classes`、`ssc_class_rounds`、`ssc_categories`、`ssc_class_category`、`ssc_sys_config`。字段级设计、两库差异请以 **《数据库设计文档_双库版_20260904》** 为权威，此处只列**对接必知差异**：

| 差异点 | 外网 `enroll_db` | 内网 `smart_academic_affairs` | 影响 |
| --- | --- | --- | --- |
| `class_rounds.period_start/end` 类型 | `DATETIME` | `VARCHAR(50)`（存 `yyyy-MM-dd HH:mm:ss`） | 跨库比对轮次时间时内容同格式、可字符串直接比对 |
| `applications.outer_id` 语义 | 存**内网**记录 id（备链路回填，主链路下多为 NULL） | 存**外网**记录 id（NASL 主链路回填） | **对账/查重/同步一律以「内网 outer_id = 外网报名 id」为桥梁**；勿用外网 outer_id 对账 |
| `classes.outer_id` 语义 | 存内网班级 id | 存外网班级 id | 方向相反，同上 |
| `enrolled` 字段 | 注释「已弃用」 | 注释「冗余字段」 | 结构都有该列，但**非权威计数**，勿当录取人数统计依据 |
| `applications` 索引 | 全（id_card/phone/status/class/…） | 仅 id_card、class_id | 内网筛选走低代码平台，不依赖 DB 索引 |

### 5.2 状态机（**以 0–4 为准**，务必牢记）

```
0 = 未报名        （占位/初始，学生端不直接出现）
1 = 审核中/已报名  （学生提交成功后的默认态）
2 = 已撤回        （学生自己撤回 / 管理员批量软删也落到 2，见第十一节）
3 = 已录取        （管理员在录取配置中批量录取）
4 = 未录取        （管理员批量未录取，终态）
```

- 语义：`1 → 2/3/4` 为正常流转；`3`（录取）与 `4`（未录取）为**终态**（学生端不能再撤回，也**不会被后续同步用外网状态覆盖**，见第七节保留规则）。
- **另一独立机制 `is_deleted`**（0=正常 / 1=管理员软删除）：与 `status=2`（学生撤回）是**两套独立机制**，不要混淆。

> ⚠️ 注：历史文档（CLAUDE.md、低代码平台接口文档 v1、00-项目学习手册）中曾用旧说法「1=已报名 0=已撤回 2=已录取」或「status→0 表示撤回」。**以本文 0–4 状态机为准**，旧说法一律视为过时。

### 5.3 outer_id / 内外网对账铁律

- **脱敏后的身份证/手机号（`id_card_masked`）不能作查询/对账条件**——库里存的是完整值，脱敏值用于显示。
- 内网 `outer_id` = 外网记录 id，是对账、查重、同步状态比对的**唯一可靠桥梁**。
- 详细对账 SQL、查重 SQL 见 `docs/2026-09-01-重复报名排查与修复.md` 与 `tmp/dup_check_*.sql`（注意脱敏，勿泄露完整手机号/身份证）。

## 六、业务规则与边界

以下为学生端当前线上生效规则（经 9-01 排查 + 后端代码确认）：

1. **每生有效报名数**：不是「最多 N 个班」的硬上限，而是**全局唯一防重**——同一身份证 / 手机号**同时只能有 1 条 `status ∈ {1(审核中), 3(已录取)}` 的有效报名**（无论报哪个班）。
   - 想报新班：必须先撤回当前有效报名（→ 2），或等上一班被处理为 3/4 后。
   - 报名冲突校验接口 `/api/applications/check` 返回 `hasIdCardConflict / hasSameClassConflict / hasPhoneConflict` 等，前端据此拦截重复提交。
2. **撤回限制**：只有 `status=1`（审核中/已报名）且当前时间在该班级轮次 `period_end` **之前**才能撤回；已录取(3)、未录取(4) 均**不可撤回**。
3. **报名须知弹窗**：学生**主动点击**查看，非强制开屏。
4. **多轮报名**：一个班可有多轮（如成电班 id 2/3 有两轮）。后端 `getRound()` 根据服务器时间与轮次 `period_start/end` 自动判定当前报名轮次；学生端用 `/api/time` 校准本地时钟与截止判断**同一时钟源**，防止本地时间篡改。
5. **报名时**：`has_english` 仅 ACCA/CFA/智能财务班需填；`enrollment_year`、`round`、`source=student` 由后端自动写入。

## 七、数据同步机制（核心）

> 低代码端同步**不走** enroll-server 的 `syncFromLowCode`（`/api/admin/sync/applications`，那是备链路）。**主链路是低代码平台 NASL 的 `dataSynchronization()`**。本文基于 9/7 采集到的完整 NASL 源码复盘，与线上一致。

### 7.1 触发方式

| 触发 | 说明 |
| --- | --- |
| **手动** | 低代码平台两个页面（报名记录管理 / 特色班报名后台管理）的「数据同步」按钮 → 都调同一个 `dataSynchronization()` |
| **定时** | 把 `dataSynchronization()` 开放为 HTTP 接口，由**任务调度中心**按 Cron 定时调用 |

**定时任务（调度中心配置，运维必读）：**

| 项 | 值 |
| --- | --- |
| 接口 | `GET http://***REMOVED***:8493/rest/specialClassDataSynchronization`（内网地址，仅内网可达） |
| Cron | `0 0 0,8,12,17 * * ?`（每天 0/8/12/17 点整点，共 4 次/天） |
| 执行器 | 正式环境；运行模式 BEAN `HttpJobHandler` |
| 路由 / 阻塞 | 路由=故障转移；调度过期=立即执行一次；阻塞处理=单机串行 |
| 状态 | **当前正在运行** |

> ⛔ **运维红线（务必执行）**：
> **报名季结束后，必须关闭该定时任务**——否则会在非报名期继续周期同步（此时内网/外网报名数据无新变化，仍会空跑、并可能把非报名期的内网改动用旧规则回推到外网，或与下一年度初始化冲突）。
> **下次报名开始前，再开启它**。建议把「开启/关闭定时同步」列为每届报名工作的起止动作，纳入流程清单，避免遗忘。

### 7.2 完整同步流程（`dataSynchronization()` 10 步）

> 数据源命名：NASL 里 `apis::RegistrationforFeaturedClasses`/`full_coverage(_two)`/`notice_get` 是低代码平台对**外网 enroll-server HTTP API** 的建模别名；`app::dataSources::defaultDS::entities::SscXxx` 是内网库实体。

1. **登录拿凭证**：内网 `app::logics::login()` → 取外网 `POST /api/auth/login` 返回体 `token`，拼 `Authorization: Bearer <token>`。
2. **拉外网**：`GET` 报名须知（`notice_get`）；`GET` 报名记录全量（`/api/admin/applications/all`，仅返回 `is_deleted=0`、不分页）。
3. **读内网**：`getInnerCategories / getInnerClasses / getInnerNotice / getInnerApplications` + 内网全部 `class_rounds` + 全部 `class_category`。
4. **报名须知比对推送**：内网 `sys_config` 与外网须知的 `title/conditions/notices/contactInfo` 任一不同才 `POST` 推外网（只更新有变化的）。
5. **类别全量覆盖外网**：把内网全部类别 `POST /sync/categories`（外网清空重建，按类别 name 为键）。
6. **班级全量覆盖外网**：把内网每个班连同其轮次（拼成 `classRounds`）+ 类别名（`categoryNames`）一起 `POST /sync/classes`；外网用 `innerId`（=内网班级 id）回填 `classes.outer_id`。→ **班级/类别这里是「内网权威 → 推外网」**。
7. **报名记录重建（Applications，最复杂）**：
   - **备份**：在清空内网前，把内网已有记录的 `status` 按 `outerId`（=外网记录 id）备份到 `statusMap`，`auditComment` 备份到 `commentMap`。
   - **清空**：`SscApplicationsEntity::deleteBy(______)` 清空内网 applications。
   - **重建**：遍历外网全量数据，`outerId` 在 `statusMap` 中 → **仅当备份 status 为 3 或 4 时保留内网值**（管理员手动录取/驳回结果不能被覆盖），**1/2 一律用外网最新 status**；`outerId` 不在 `statusMap`（首次）→ 用外网 status。`auditComment` 优先取内网 `commentMap` 备份，否则取外网值。其余字段 `idCardRaw`(完整证号)、`idCard`(脱敏)、`applyTime`(转格式)、`classId=outerApp.innerId` 等照外网写入，`batchCreate` 落内网。
   - ⚠️ 这套「1/2 用外网、3/4 保留内网」是 9/1 修复后的规则，**保证学生撤回（2）能同步到内网，又保证内网录取/驳回结果不被同化**。
8. **录取回推外网**：重建后扫内网 `status==3` 且有 `outerId` → 按 `auditComment` 分组 → 分批 `POST /api/admin/applications/admit`。
9. **未录取回推**：扫内网 `status==4` → 按 `auditComment` 分组 → `POST /api/admin/applications/reject`。
10. **软删回推**：扫内网 `isDeleted==1` 且有 `outerId` → 收集 outerId → **按 100 条/批切片** → `POST /api/admin/applications/delete`。

### 7.3 权威方向分层（务必理解，别弄反）

| 数据类型 | 权威方 | 方向 |
| --- | --- | --- |
| 班级、类别、班级-类别、轮次 | **内网**（低代码端维护） | 内网 → 推外网（全量覆盖） |
| 报名须知(sys_config) | **内网** | 内网 → 外网（有差异才推） |
| **学生报名数据**（applications 主体） | **外网**（学生报名写入） | 外网 → 拉回内网重建 |
| **录取/未录取结果 + 审核意见** | **内网**（管理员操作） | 内网 → 回推外网（admit/reject） |
| **软删状态** | **内网**（管理员软删） | 内网 → 回推外网（delete） |

即：**「班级/类别/须知 = 内网权威」，「学生报名数据 = 外网权威」，「录取结果与软删 = 内网权威」** 三条线不冲突，分层各管各的。

### 7.4 同步侧的防重 / 容错加固（9/1，jar 已打）

- `syncFromLowCode` 加**全局唯一防重**（`seenAppliedIdCard / seenPhone` 双 Set + DB 兜底），杜绝同一身份证/手机号被重复入库。
- `batchAdmit / batchReject` 改**容错版**：逐条判断，非审核中(非 1)的跳过，**避免「全有或全无」连累整批**。
- `SyncController` 补 `/applications` 端点。
- 9/3 对账验证：已录取(3) 30 条内外网全对齐，无被同化。

## 十一、报名记录软删 / 恢复同步链路

- **`StudentRegistrationRecordManagement`（报名记录管理）** 页面支持按年份查看、**批量软删除 / 恢复**报名记录。
- 这里的「软删」是在**内网**把记录 `is_deleted` 置 1；**同步到线上**依靠 `dataSynchronization()` 第 10 步（软删回推）：收集内网 `isDeleted==1` 且有 `outerId` 的记录 → 按 **100 条/批** `POST /api/admin/applications/delete` → 外网把对应记录 **status 置 2（已撤回）**。
- 因此一句话：**内网软删 = 想让线上那条报名“消失”（落到已撤回）**。
- ⚠️ **恢复的边界（接手注意）**：若某条已被软删并同步到线上（外网 status=2），之后再在内网「恢复」（is_deleted 置 0）并再次同步，由于外网 `applications/all` 只返回 `is_deleted=0` 的记录、被处理后该记录已不在拉取重建范围，**恢复不一定能让该记录在外网以原状态重新可见**。**误删恢复属高风险操作，务必先小样本实测行为，再决定是否批量恢复**，不要凭文档假设直接批量操作生产数据。

## 十三、踩坑与运维红线

### 13.1 运维红线（务必照做）

1. ⛔ **报名季结束 → 关闭定时同步任务**；下次报名开始前 → 开启。调度中心 Cron `0 0 0,8,12,17 * * ?`（见 7.1）。此条是每届报名工作的起止动作，建议列入流程清单。
2. ⛔ **内网软删=想删线上那条；误删恢复属高风险**，批量前先小样本实测（见第十一节）。
3. ⛔ **管理员账号走智慧教务账号体系**；`***REMOVED*** / ***REMOVED***` 及 `admin_token` 仅开发/同步 API 凭证用途，生产不向管理员开放登录。
4. ⛔ **涉及个人文件目录、真实个人数据的查重/清理 SQL 一律脱敏执行**，身份证/手机号完整值不得落盘外发（`tmp/dup_check_privacy.sql` 即脱敏版）。

### 13.2 已沉淀的坑（接手快速避雷）

| 坑 | 现象 / 根因 | 对策 |
| --- | --- | --- |
| 时区不一致 | 报名截止判断错乱 | 学生端统一用 `/api/time`（MySQL NOW()）校正本地时钟；DB 时间由 MySQL 写，不依赖 JVM 时区 |
| `applications/all` 只返 `is_deleted=0` | 软删/恢复边界异常 | 见第十一节警告 |
| 状态被「同化」 | 旧 NASL 用外网状态覆盖内网 3/4 录取结果 | 已修复为「1/2 用外网、3/4 保留内网」（7.2 step7） |
| batchAdmit/Reject 全有或全无 | 单条异常连累整批 | 已改容错版逐条跳过非审核中（7.4） |
| 同步重复入库 | 同一身份证/手机号被插多条 | 已加全局唯一防重（7.4） |
| CORS/代理 | 前后端联调 404/跨域 | 端口 8081/5173；proxy `/api → 8081`；api.js 顶部 8080 注释为误导 |
| 前端登录态 | Cookie 化未对齐 | 前端仍 localStorage + Bearer header（3.2） |
| `enrolled` 列口径两库不一 | 误当录取人数统计 | 以实时查询/同步结果为准（5.1） |
| 历史文档旧状态机 | 0–2 / 1-0-2 旧说法 | 以 0–4 为准（5.2） |
| 后端日志级别全 OFF | `application.yml` 里 root / `com.enroll.server` / hibernate 等 logging 级别全 `OFF` → 启动失败也**无任何输出**，难排查 | 排查启动问题改依赖端口监听（`netstat -ano \| findstr 8081`）判断是否起来，或临时调高日志级别 |
| Git Bash 杀进程 | `cmd //c` / `taskkill //F` 有兼容问题（cmd 打开即返回不执行） | 杀进程用 PowerShell `Stop-Process -Id <PID> -Force` 最稳 |
| 后端端口随机化 | Tomcat 起在随机端口（如 61923）而非 8081 | 曾因 `-Dspring-boot.run.arguments` 传参异常导致；显式传 `--server.port=8081` |
