## 二、维护方案（P0 详细展开）

### P0-1：SMS 配置外置

**问题**：短信网关账号密码写死在 `AuthService.java`，泄露风险高。

**修复步骤**：

1. `application.yml` 新增配置段：
```yaml
sms:
  sn: "SDK-BBX-010-39560"       # 从环境变量取
  pwd: "${SMS_PWD}"             # 生产用环境变量注入，不用放代码
  url: "http://***REMOVED***:8061/mdsmssend.ashx"
  sign: "【杭州电子科技大学信息工程学院】"
```

2. `AuthService.java` 改造：
```java
@Value("${sms.sn}")
private String smsSn;

@Value("${sms.pwd}")
private String smsPwd;

@Value("${sms.url}")
private String smsUrl;

@Value("${sms.sign}")
private String smsSign;
```

3. 删掉代码里的硬编码默认值

**验证**：改完后本地启动后端，调用 `/api/auth/send-code`，确认短信发出。

### P0-2：数据库索引

**问题**：`applications` 表的 `id_card`、`phone`、`status` 字段查询无索引，数据量大时慢。

**修复 SQL**：
```sql
-- 文件：docs/sql/V20260704__add_application_indexes.sql

-- 身份证查询（学生查自己报名、管理端按身份证搜）
ALTER TABLE ssc_applications ADD INDEX idx_id_card (id_card);

-- 手机号查询（学生验证码登录、管理端按手机号查）
ALTER TABLE ssc_applications ADD INDEX idx_phone (phone);

-- 状态筛选（管理端按状态筛选报名记录）
ALTER TABLE ssc_applications ADD INDEX idx_status (status);

-- 联合索引：学生按身份证+状态查（效率最高）
ALTER TABLE ssc_applications ADD INDEX idx_id_card_status (id_card, status);

-- 联合索引：管理端按班级+状态查
ALTER TABLE ssc_applications ADD INDEX idx_class_status (class_id, status);
```

**验证**：`EXPLAIN SELECT * FROM ssc_applications WHERE id_card = 'xxx' AND status IN (1,3)` 看到 `Using index` 即生效。

### P0-4：统一 ID 解析工具

**问题**：各 Controller 从 `Map body.get("id")` 强转 Integer，字符串 `"1"` 会炸 `ClassCastException`。

**修复方案**：在 `GlobalExceptionHandler.java` 或新建 `RequestUtils.java`：

```java
public static Integer parseId(Map<String, Object> body, String key) {
    Object val = body.get(key);
    if (val == null) {
        throw new BusinessException(ResultCode.PARAM_INVALID, key + " 不能为空");
    }
    if (val instanceof Integer) return (Integer) val;
    if (val instanceof String) {
        try { return Integer.parseInt((String) val); }
        catch (NumberFormatException e) {
            throw new BusinessException(ResultCode.PARAM_INVALID, key + " 必须是数字");
        }
    }
    throw new BusinessException(ResultCode.PARAM_INVALID, key + " 格式错误");
}
```

各 Controller 的 `Integer id = (Integer) body.get("id")` 全部替换为 `parseId(body, "id")`。

## 三、之前评估没考虑到的地方（***REMOVED***补充）

### 1. 前端 `api.js` 的 Mock 数据污染

**问题**：`fetchClasses()` 后端连不上时返回硬编码 mock 数据，字段是 `"2026/01/01 - 2026/12/31"`（始终显示"报名中"）。开发和测试环境会误以为数据正常。

**风险**：后端挂了，前端看起来"一切正常"，只是看不到真实班级。

**建议**：mock 数据加注释 `// ⚠️ 后端未启动时兜底，不要用于生产测试`，或改成抛异常不返回数据。

---

### 2. CORS 生产域名配置风险

**问题**：`WebMvcConfig.java` 第40-42行，生产域名从环境变量 `CORS_ALLOWED_ORIGINS` 读取，但代码里默认值是 `localhost:5173`。如果生产环境变量没配，CORS 直接漏成 `localhost`，外网前端请求全被拦。

**风险**：部署时忘了配环境变量 → CORS 全失效 → 外网学生无法报名。

**建议**：启动脚本里强制校验环境变量，没配则启动失败并提示。

---

### 3. 报名限额 `quota = -1`（不限名额）的边界没校验

**问题**：`ClassInfoRepository.incrementEnrolledIfQuotaAvailable` 的 SQL 条件是 `quota = -1 OR enrolled < quota`，-1 被当成"不限"的魔法数字。但如果管理员误设 `quota = -2`，逻辑会乱（-2 < enrolled 永远成立，可以无限报）。

**建议**：在 `ClassService.createClass / updateClass` 里加校验：
```java
if (quota != -1 && quota < 0) {
    throw new BusinessException(ResultCode.PARAM_INVALID, "名额必须为 -1（不限）或正整数");
}
```

---

### 4. `periods` JSON 解析失败时静默 fallback 有隐患

**问题**：`ApplicationService.determineCurrentRound()` 解析 JSON 失败时，打 `log.warn` 然后 fallback 到 `cls.getPeriod()` 判断。如果 JSON 格式损坏，管理员不知道（没通知），班级看起来"报名正常"但轮次判断逻辑实际错了。

**建议**：JSON 解析失败时主动写一条错误日志到 `sys_config` 告警，或者在 `ClassService` 保存班级时做 `periods` 格式校验。

---

### 5. 前后端 `status` 类型不一致

**问题**：数据库存 `status` 是 `INT` (0/1/2/3/4)，Java 实体是 `Integer`，前端 `api.js` 返回的 `status` 是 `String`（`ApplicationDTO.toString()` 里 `.status(String.valueOf(e.getStatus()))`）。

**隐患**：低代码平台调 API 时容易混淆，不知道该用数字还是字符串做判断。

**建议**：统一在 `R.java` 响应层面说明 `status` 类型，或在文档里注明"统一用数字"。

---

### 6. 密码登录的密码用明文比较

**问题**：`AuthController.java` 第61行 `password.equals(inputPassword)`，如果密码是 MD5 存的，比较也是明文比，存在时序攻击风险（虽然低风险）。

**建议**：用 `MessageDigest.isEqual(byte[], byte[])` 做恒定时间比较。

---

### 7. 前端没有防止重复提交

**问题**：学生点"提交报名"后，网慢的情况下按钮没变灰，可能重复提交两次。

**建议**：FormPage 提交时按钮加 loading 状态，提交中禁用按钮。

---

### 8. 管理端批量操作没有事务回滚

**问题**：`ApplicationService.batchAdmit(ids)` 调用 `batchUpdateStatus(ids, STATUS_ENROLLED)`，这是 JPA 批量更新。如果中途网络抖动，可能只更新了部分 ID。

**建议**：确认 Repository 的 `@Modifying` 方法是否在同一个 `@Transactional` 事务内，批量 SQL 建议加 `@Transactional(propagation = Propagation.REQUIRED)`。
