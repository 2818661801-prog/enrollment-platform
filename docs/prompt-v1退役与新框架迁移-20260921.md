1. `git diff -- "*.java"` 通读 3 处未提交修复的语义：

2. 在 `release/v1` 上存档：`git add -A && git commit -m "wip: v1 线上热修复存档（退役前抢救）"`；同时 `git diff HEAD~1 -- "*.java" > docs/v1-hotfix-20260921.patch` 留底并一并提交。**先存档，后动任何分支。**
3. 切到 `refactor/architecture-cleanup`，把这 3 处修复的**语义**移植进新架构。移植落点（已核实，别找错门）：

### Phase 2 · 业务规则冲突裁决（写进文档 + 全局核对）
两个提交对「被驳回后能否重新报名」方向相反：
- v1 `bda3348`（8/6，旧线上行为）：未录取后**允许**重新报名；
- refactor `dc9c0b7`（8/23，新框架行为）：被驳回后同一身份证/手机号/同班**禁止**重报。

v1 已退役，**以"禁止同班重报"为准**。⚠️ 语义边界（写 ADR 和核对代码时严格区分）：禁的是"被驳回后重报**同一个班**"；"被驳回后报**其他班**"两版都是允许的（v1 代码注释明确"被驳回(4)后应能报其他班，所以这里不查 STATUS_REJECTED"）——不得扩大化禁止，那是改需求不是修 bug。要求：
1. 新建 `docs/ADR-驳回后禁止重报.md`：记录冲突两方、裁决结果（同班禁、他班放）、理由（单一主线、新框架规则更严格且与防重三层一致）。
2. 全局 grep `STATUS_REJECTED` 与查重相关逻辑（submit、checkDuplicate 三层防重），确认代码与测试断言**没有残留**按"允许同班重报"行事的路径，也没有把"报其他班"误禁掉的过度拦截；有则修正并跑对应测试证明。

### Phase 3 · 新框架收尾（让它配得上"完成"两个字）
1. **全量验证**：后端 `mvn test`（enroll-server 目录）、前端 `npm run test` + `npm run build`（enroll-web 目录）。逐条列出实际执行的命令、退出码、关键输出。做不到全绿就如实写"哪些失败、为什么"，**不许口头宣称通过**。
